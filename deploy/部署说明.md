# 部署说明（腾讯云 4 核 4G）

本文记录把 CloudDrive 部署到一台 4 核 4G 云服务器的完整步骤，
包括资源分配依据、每一步的验证方法，以及几个必然会遇到的坑。

---

## 1. 这台机器够不够用

够，而且还有余量。内存分配如下：

| 组件 | 分配 | 说明 |
|---|---|---|
| JVM 堆 | 1 GB | `-Xmx1g`，本项目不做大对象缓存，够用 |
| JVM 堆外（元空间、线程栈、直接内存） | ~400 MB | 按经验预留 |
| MySQL 8 | ~700 MB | `innodb_buffer_pool_size=512M` |
| Redis | ~256 MB | 只放元数据缓存与锁，实际用量远低于此 |
| Nginx | ~20 MB | 静态文件 + 反代 |
| 操作系统 | ~500 MB | |
| **合计** | **约 2.9 GB** | 4 GB 下留约 1 GB 余量 |

CPU 4 核对这个负载是富裕的：上传下载是 IO 密集型，MD5 计算才吃 CPU，
而单个用户的上传速度先被带宽卡住。

**真正的瓶颈是带宽和磁盘，不是 CPU 和内存**：

- 轻量应用服务器通常 3–5 Mbps，传 100 MB 文件要 3–5 分钟。答辩演示用小文件。
- 分片上传时同一份数据会短暂存在三处：各分片、合并出的临时文件、最终对象。
  传一个 500 MB 的文件峰值需要约 1.5 GB 磁盘。系统盘一般 50 GB，
  建议把 `CLOUD_DRIVE_STORAGE_ROOT` 指到单独挂载的数据盘。

## 2. 准备服务器

安全组放行 **22（SSH）** 和 **80（HTTP）**。
**不要**放行 8080、3306 和 6379——后端、数据库和 Redis 只需本机访问，
对公网开放的 MySQL/Redis 是最常见的入侵入口。

```bash
# 以 Anolis / CentOS / 阿里云 Linux 为例，Ubuntu 把 yum 换成 apt
sudo yum install -y java-17-openjdk mysql-server redis nginx
sudo systemctl enable --now mysqld redis nginx
java -version   # 必须是 17
```

## 3. 建库建账号

应用用专用账号，不要用 root：

```sql
CREATE DATABASE cloud_drive DEFAULT CHARSET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'clouddrive'@'127.0.0.1' IDENTIFIED BY '换成强口令';
GRANT ALL PRIVILEGES ON cloud_drive.* TO 'clouddrive'@'127.0.0.1';
FLUSH PRIVILEGES;
```

表结构不用手建，应用启动时 Flyway 会执行 V1~V10 自动建好；已有数据库自动升级。邮箱、管理员及 DeepSeek 配置见 [新增功能配置说明](新增功能配置说明.md)。

把 `mysql-clouddrive.cnf` 和 `redis-clouddrive.conf` 里的参数合并进各自的配置文件，
然后重启这两个服务。

## 4. 本地打包

在你自己的 Windows 机器上打包，不要在服务器上编译——
4 GB 内存跑 Maven 构建容易触发 OOM，而且服务器上还要再装一套 Maven 和依赖。

```powershell
# 后端：产出 target\cloud-drive-learning-0.1.0-SNAPSHOT.jar
cd C:\path\to\cloud-drive\clouddrive
mvn -Dmaven.repo.local=C:\Environment\m2repo clean package -DskipTests

# 前端：产出 dist 目录
cd ..\clouddrive-ui
npm install
npm run build
```

## 5. 上传与目录结构

```bash
sudo useradd -r -s /sbin/nologin clouddrive
sudo mkdir -p /opt/clouddrive/{logs,www} /data/clouddrive/{objects,chunks,snapshots}
sudo chown -R clouddrive:clouddrive /opt/clouddrive /data/clouddrive
```

把这些文件传上去（scp 或宝塔面板都行）：

| 本地 | 服务器 |
|---|---|
| `clouddrive/target/*.jar` | `/opt/clouddrive/app.jar` |
| `clouddrive-ui/dist/*` | `/opt/clouddrive/www/` |
| `deploy/clouddrive.env.example` | `/opt/clouddrive/clouddrive.env`（改好口令） |
| `deploy/clouddrive.service` | `/etc/systemd/system/clouddrive.service` |
| `deploy/nginx-clouddrive.conf` | `/etc/nginx/conf.d/clouddrive.conf` |

配置文件里有口令，权限必须收紧：

```bash
sudo chmod 600 /opt/clouddrive/clouddrive.env
sudo chown clouddrive:clouddrive /opt/clouddrive/clouddrive.env
# JWT 密钥用随机值，不要用示例里的字符串
openssl rand -base64 48
```

## 6. 启动

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now clouddrive
sudo systemctl status clouddrive

# 看启动日志，应该出现 "Successfully applied 8 migrations" 和 "Tomcat started on port 8080"
sudo journalctl -u clouddrive -f

sudo nginx -t && sudo systemctl reload nginx
```

验证顺序（从里到外，哪一层坏了一目了然）：

```bash
curl http://127.0.0.1:8080/actuator/health     # 后端本身
curl http://127.0.0.1/actuator/health          # 经过 Nginx
# 浏览器打开 http://服务器公网IP  → 应看到登录页
```

### 发码来源地址与可信代理

部署环境文件必须包含 `SPRING_PROFILES_ACTIVE=deploy`。该 profile 将后端绑定到
`127.0.0.1:8080`，通过 Tomcat 原生转发头处理，仅信任 `127.0.0.1` / `::1` 本机代理，
不信任整个私网；默认开发 profile 不解析任何转发头。配套 Nginx 会覆盖
`X-Forwarded-For` 为实际连接的 `$remote_addr`，并覆盖或清除其他转发头，
不能改成直接信任客户端提供的头。这样不同真实来源 IP 使用不同发码请求限流桶，
同时保留同一邮箱/用途的发送冷却，不能只用邮箱限流替代来源 IP 限流。

更新已有部署时，应同时更新 JAR、环境文件和 Nginx 配置，然后重启应用并重载 Nginx。
用 `ss -lntp | grep ':8080'` 确认仅监听 `127.0.0.1:8080`，且安全组不开放 8080。
若 Nginx 前还有 CDN/负载均衡，或代理和后端不在同一主机，本样例不能直接沿用：
需先限定真实可信代理地址并正确设置 Nginx real_ip，再调整后端绑定与网络访问控制。
同一 NAT 出口的用户仍自然共享来源 IP；这与全站共享本机代理桶不同。

## 7. 必踩的坑

**上传大文件返回 413**
Nginx 默认 `client_max_body_size 1m`。配置里已经改成 1024m，
但如果你用宝塔面板，面板可能有自己的一份全局配置会覆盖站点配置，要一起改。

**上传进度条瞬间 100% 然后卡住**
`proxy_request_buffering` 没关。Nginx 先把整个请求体收到自己的临时文件，
浏览器那端早就传完了，后端却还没开始处理。配置里已关闭。

**502 Bad Gateway**
先 `systemctl status clouddrive` 看后端在不在。常见原因是数据库口令错、
Redis 没设口令而应用配了（或反之），日志里能直接看到连接失败的栈。

**中文文件名乱码**
`-Dfile.encoding=UTF-8` 已在 systemd 里指定；数据库必须是 utf8mb4；
下载响应头用的是 RFC 5987 的 `filename*`，已在代码里处理。

**时间差 8 小时**
JDBC URL 的 `serverTimezone=Asia/Shanghai`、MySQL 的 `default-time-zone=+08:00`、
JVM 的 `-Duser.timezone=Asia/Shanghai` 三处要一致，少一处都会错开。

## 8. 上线前的安全检查

- [ ] JWT 密钥换成随机值，不是示例字符串
- [ ] MySQL、Redis 都设了口令，且只监听 127.0.0.1
- [ ] 安全组没有放行 8080 / 3306 / 6379
- [ ] 启用 deploy profile，后端仅监听 127.0.0.1:8080，Nginx 覆盖外来转发头
- [ ] `clouddrive.env` 权限是 600
- [ ] 应用以专用低权限账号运行，不是 root
- [ ] `/actuator/` 除 health 外未暴露到公网（Nginx 已配置 404）

**没有配 HTTPS 的后果要清楚**：当前是纯 HTTP，登录口令和 JWT 都在明文传输。
作为课程演示可以接受，但文档里应当如实写明这是已知缺口；
真要长期挂在公网上，应当用域名 + Let's Encrypt 免费证书把它补上。
