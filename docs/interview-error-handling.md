# 面试讲解：HTTP 错误状态与统一异常处理

## 这个改进解决了什么

原来的 `GlobalExceptionHandler` 返回 `Result.error(...)`，但没有设置 HTTP 状态。密码错误等业务失败虽然在 JSON 中返回 `code: 400`，HTTP 层仍然是 `200 OK`。HTTP 监控和只检查状态码的客户端因此无法正确区分成功与失败。

另外，错误 JSON 或不能转换的字段类型会落入通用异常处理，响应体标成系统异常；`SystemException` 的内部诊断信息也会直接返回给客户端。

## 具体改动

| 场景 | HTTP 状态 | 响应体 |
|---|---|---|
| 正常请求 | 200 | 保留 `code/message/data` 成功结构 |
| 业务异常 | 400 | 保留业务异常的 code 和可读 message |
| Bean Validation 校验失败 | 400 | 返回校验提示 |
| 非法参数 | 400 | 返回参数提示 |
| JSON 无法解析、字段类型不匹配 | 400 | 返回固定提示，不返回解析器内部信息 |
| 系统异常、未预期异常 | 500 | 返回固定提示；详细异常留在服务端日志 |

通过 `@ResponseStatus` 设置 HTTP 状态，继续用 `Result` 统一响应体。HTTP 状态与应用业务码是两个层次，例如业务码 `10001` 可以对应 HTTP 400，不直接把业务码当作 HTTP 状态。

前端 `frontend/index.html` 的 `api()` 使用 Fetch 并解析响应中的业务码；Fetch 不会仅因为 HTTP 400/500 自动抛出异常，因此原有错误提示仍可读取 `message`。

## 如何验证

在仓库根目录运行：

```bash
mvn -B -pl common test
```

测试位于 `common/src/test/java/com/base/common/web/GlobalExceptionHandlerTest.java`。MockMvc 通过实际的请求解析、Bean Validation 和 ControllerAdvice 流程验证 HTTP 状态与 JSON 响应，而不是只调用异常处理方法。

10 个测试用例覆盖业务异常、自定义业务码、校验失败、两类错误 JSON、非法参数、系统异常、自定义系统码、未预期异常和成功请求。测试使用专用测试 Controller，不启动数据库、Redis、Nacos 或模型服务。

### 验证记录（2026-10-25）

- 修复前：10 个用例中有 9 个因 HTTP 状态仍为 200 而失败。
- 修复后：使用 JDK 17 运行 `mvn -B -pl common test`，10 个用例全部通过。
- 全仓 `mvn -B verify` 在 `file-service` 打包时失败，错误为 `Unable to find main class`。本次更新前的仓库中，该模块只有 POM 和资源文件，缺少 Java 源码及启动类；完整服务运行仍需要补齐这些文件。

## 可以怎样讲

> 我在网盘项目中检查了统一异常处理，发现失败响应只改了 JSON 的业务码，HTTP 仍然返回 200。我补齐了已处理异常的 HTTP 状态，把无法解析的 JSON 归为客户端输入错误，并让系统异常返回固定提示。随后用 MockMvc 同时断言 HTTP 状态、业务码和错误信息，也验证了正常请求与自定义业务码仍保持原有格式。

讲解前应自己运行测试，能沿着“请求进入 MVC → 参数解析和校验 → 异常分类 → HTTP 状态与响应体”说明代码。讲述以本次可复现的问题和验证结果为依据，上线效果与性能指标需要另行验证。

## 追问与边界

- **为什么不只在前端判断 code？** HTTP 状态也被网关、监控、日志工具和其他客户端使用；响应体承担具体业务语义。
- **400 和 500 怎么分？** 此次将业务拒绝、校验和输入格式错误映射为 400，服务内部故障映射为 500。更细的 401、403、404、409、429 应按具体认证或业务契约另行设计。
- **为什么隐藏系统异常 message？** 它可能含内部组件和存储诊断信息；服务端保留堆栈用于排查，客户端得到稳定提示。
- **测试证明到哪一层？** 证明本次覆盖的 Spring MVC 错误契约；不代表已完成微服务联调、真实浏览器操作或生产部署验证。
- **所有异常都处理完整了吗？** 没有。此改动覆盖表中列出的异常；Gateway 使用 WebFlux，认证框架、其他框架异常和流式响应还需各自的契约测试。
