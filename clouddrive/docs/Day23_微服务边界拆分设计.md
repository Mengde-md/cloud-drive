# Day23 微服务边界拆分设计与环境冻结

> **本文是设计文档，不是已交付的代码。** 截至 Day23，系统仍然是一个单体
> （`cloud-drive-learning`），本文给出的是将来拆分时的边界、契约与取舍分析。
> 真正的服务拆分实现属于 Day24 及之后的范围，当前代码库中不存在 auth-service、
> file-service、gateway 等独立模块。

---

## 1. 为什么现在做设计而不是直接拆

单体现在只有一个部署单元、一个数据库、一次本地方法调用就能完成的事务。
拆成多个服务会立刻引入三类新成本：跨进程调用的失败与超时、跨库事务不再存在、
部署与配置从 1 份变成 N 份。在没有想清楚边界之前动手，最常见的结果是
拆出来几个"还是共用一张表"的服务——既承担了分布式的全部代价，
又没有拿到任何独立演进的好处。

因此 Day23 只做两件事：**按数据所有权把边界画出来**，**把运行环境固定下来**。

---

## 2. 边界划分：以数据所有权为准

划分服务的依据不是"功能听起来像一类"，而是**谁拥有并独占写入哪张表**。
一张表只能有一个服务写，其它服务只能通过接口读。

| 服务 | 独占写入的表 | 对外提供的能力 | 不负责什么 |
|---|---|---|---|
| auth-service | `user_account` | 注册、登录、签发与校验 JWT、口令摘要 | 不认识文件与目录 |
| user-service | （配额视图，读 `user_account`；后续独立出 `user_profile`） | 账号概览、配额查询与扣减决策 | 不写认证凭据 |
| file-service | `drive_entries`、`upload_sessions`、`upload_chunks`、`file_shares` | 目录树、上传、下载、分享、回收站 | 不签发令牌、不管理账号 |
| gateway | 无 | 统一入口、路由、令牌校验与身份透传、限流 | 不写任何业务表 |

几个边界判断的理由：

- **配额为什么跟着账号而不是文件**：配额是账号的属性（"这个人能用多少"），
  而已用量是文件的聚合（"这个人现在用了多少"）。拆开之后，
  `已用量` 必须由 file-service 提供，user-service 不能直接查 `drive_entries`——
  否则两个服务共用一张表，边界形同虚设。
- **分享表为什么归 file-service**：分享的生命周期完全依附于文件，
  文件被彻底删除时分享必须一起失效。放在别的服务里就需要跨服务的级联删除。
- **gateway 为什么不碰数据库**：网关一旦有自己的业务表，就会逐渐变成第二个单体。
  它只做与请求本身有关的事。

## 3. 服务间契约

拆分后原本的本地方法调用会变成三类跨服务交互：

| 调用 | 方向 | 同步/异步 | 失败时的行为 |
|---|---|---|---|
| 校验令牌 | gateway → auth-service | 同步（或网关本地验签） | 失败即 401，不放行 |
| 查询/占用配额 | file-service → user-service | 同步 | 失败即拒绝上传（保守策略，宁可少传不可超额） |
| 释放配额（删除、清空回收站） | file-service → user-service | 异步更合适 | 失败可重试，短时间不一致可接受 |

**令牌校验的关键取舍**：如果每个请求都让网关去 auth-service 查一次，
auth-service 会成为全链路的单点和性能瓶颈。更好的做法是
**网关本地验签**（持有公钥 / 共享密钥，自己校验 JWT 签名与过期时间），
只有注销、改密这类需要立刻生效的场景才回源。
代价是令牌在有效期内无法单独作废——这正是当前单体已经接受的同一个取舍，
拆分后它依然存在，不会因为变成微服务就自动消失。

**身份透传**：网关校验通过后，把用户 id 写进内部请求头（例如 `X-User-Id`）传给下游。
下游服务**必须只信任来自网关的内部头**，并且这些头必须在网关入口处被强制清洗——
否则外部调用方自己伪造一个 `X-User-Id` 就能冒充任何人。这是拆分后最容易出的安全事故。

## 4. 要不要引入消息队列（MQ）

### 4.1 结论

**当前阶段不引入。** 现有的业务动作（上传、删除、分享）都需要用户立刻看到结果，
天然是同步语义；引入 MQ 只会把"用户点了删除但列表里还在"变成正常现象，
同时多出一个必须运维的中间件。

**将来值得引入的场景**是那些"调用方不需要等结果"的动作：

- 彻底清空回收站后的磁盘对象回收（慢、可重试、用户不关心何时完成）；
- 文件索引同步（例如后续接入 Elasticsearch 的检索索引）；
- 操作审计与统计。

### 4.2 一旦引入，必须同时处理的四件事

| 问题 | 不处理会怎样 | 处理方式 |
|---|---|---|
| **幂等** | MQ 至少投递一次，重复消费会把同一个对象删两次、同一条记录插两次 | 消息带业务唯一键，消费端先查后写或依赖数据库唯一约束；消费逻辑本身必须可重复执行 |
| **重试** | 瞬时故障（数据库抖动）导致消息被直接丢弃 | 有限次数 + 指数退避重试；区分"可重试"（超时、连接失败）与"不可重试"（参数非法）两类失败 |
| **顺序** | "创建后立刻重命名"两条消息乱序，最终名字是旧的 | 按业务实体分区（同一 entryId 进同一分区/队列）；或让消息携带版本号，消费端丢弃比当前版本旧的消息 |
| **死信** | 一条毒消息无限重试，阻塞整个队列 | 配置死信队列，超过重试上限转入 DLQ，并对 DLQ 堆积告警——**没有人看的死信队列等于没有死信队列** |

这四件事是一个整体：只做幂等不做死信，队列仍然会被毒消息堵死；
只做重试不做幂等，重试本身就会制造脏数据。

## 5. 拆分后消失的东西：跨库事务

当前单体里 `DocumentUploadApplicationService.upload()` 依赖一个本地事务：
配额校验和元数据插入要么一起成功、要么一起回滚。
一旦 user-service 和 file-service 各自持有数据库，这个事务就不存在了。

可选方案与代价：

| 方案 | 说明 | 代价 |
|---|---|---|
| 不拆配额 | 把配额数据留在 file-service | 边界不纯粹，但最简单可靠 |
| TCC / Saga | 先预占配额，失败再补偿释放 | 需要写补偿逻辑，并处理"补偿也失败"的情况 |
| 最终一致 | 先写文件，异步扣减配额 | 存在短暂超额窗口，需要对账任务 |

本项目的倾向是：**先选"不拆配额"**，等到真的有独立演进需求时再上 Saga。
这条取舍本身就是答辩时值得讲的内容——能说清"为什么不拆"比硬拆更有说服力。

## 6. 环境冻结（Day23 的硬性门槛）

拆分之前必须先保证依赖能被一条命令拉起来，否则每加一个服务，
"在我机器上能跑"的问题就会被放大一次。

已冻结的方案见仓库根目录：

- `docker-compose.yml` —— MySQL 8.0 + Redis 7，都带 healthcheck；
- `.env.example` —— 所有口令、端口、连接串的占位样例；
- `application.yml` —— 全部通过 `${环境变量:默认值}` 读取，**代码里没有任何个人凭据**。

验证步骤：

```bash
cp .env.example .env          # 修改其中的口令
docker compose up -d
docker compose ps             # 两个服务都应为 healthy
mvn spring-boot:run           # 应用连上容器里的 MySQL/Redis，Flyway 自动建表
```

数据库结构不靠手工建表，而是由 `src/main/resources/db/migration/V1~V7` 的
Flyway 迁移脚本生成——这保证了任何一台新机器拉起来的库结构都完全一致。
